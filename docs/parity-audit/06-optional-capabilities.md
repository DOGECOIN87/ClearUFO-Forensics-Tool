# Optional capabilities parity audit: AI/MCP, capture, configuration, network boundary and navigation

**ID:** `optional-capabilities`
**Reference:** original browser implementation (intended behavior)
**Native target:** `android-native/` (Expo/React Native; offline PNG milestone)

## Scope

- **Web:** `src/ai/{agent,markdown,providers,schema,settings,sse,tools,types}.ts`, `src/mcp/{index,catalog,client,oauth,servers}.ts`, `src/app/{App,context,actions,capture}.ts`, `src/panels/{AiPanel,McpDialog}.ts`, and directly relevant shared filter/project/export modules.
- **Native:** requested `android-native/app/`, `android-native/lib/_core/`, `app.config.ts`, `package.json`, and `README.md`; also screen-imported `lib/project/evidenceIO.ts`, `lib/engine/imagePipeline.ts`, and `tests/forensics/imagePipeline.test.ts` to ground claims about current evidence handling. No files were changed outside this report. No dependencies were installed and no runtime tests were run.

## Original browser capabilities (product behavior)

- **AI assistant:** configurable OpenAI, Anthropic, Gemini, OpenRouter, Ollama, LM Studio and custom OpenAI-compatible endpoints; model discovery, manual model entry, connection test, API-key show/remember/forget, and provider/server URL overrides. Requests stream to the selected provider. Local Ollama/LM Studio endpoints are available; the browser sends requests directly to providers, not through a ClearUFO server.
- **Agent interaction and safeguards:** Agent mode can inspect, navigate, and modify the project through typed tools; Ask mode supplies read/navigation/question tools only. Changes are undoable; write approvals can be automatic or per-action, requests have a step limit and can be stopped/rolled back to a checkpoint. The transcript shows tool steps, results, questions, approvals, and frame-consent prompts; requests/actions are added to project AI audit history and the processing report. User can attach the current rendered frame to a prompt. Model frame access is separately configured as ask/allow/never; each attachment/tool-shared frame is tracked. The app explicitly describes what metadata, project structure, measurements and images leave the device.
- **AI tools:** inspect project/source metadata, filter catalog/schemas, frame statistics and (with consent) rendered frame images; select chain/filter, navigate frames, control playback/range, view scaling/selection; add/adjust/reorder/enable/remove filters and manage chains, bookmarks, case info, undo/redo; open media/sample case and prepare image/video/snapshot/project/report exports with the examiner's click. Filter parameters are schema-validated and writes return a render check. The AI's visual `view_frame` and attached image are model-facing previews, not a forensic pixel verification or independent evidence interpretation.
- **MCP in both directions:** as client, configure/test remote MCP servers (Streamable HTTP, legacy HTTP+SSE, bridge-hosted servers), per-server tools, approval/trust, bearer headers/tokens and OAuth 2.1/PKCE sign-in/refresh; elicitation, progress, tool-change handling and third-party result labeling are supported. As server, the local bridge exposes the same workbench tools/resources/prompts; the browser also supports WebMCP and `window.lucid.mcp` page API. Examiner controls external access (off/read/ask/full), per-client connection grant, read-only grants, frame consent, approvals and audit logging. The bridge can expose stdio or non-CORS servers and supplies client configuration snippets.
- **Capture and navigation/configuration:** File › Video Input captures camera or screen where browser APIs permit. Lossless mode grabs frames into uncompressed RGB24 AVI and reports skipped frames/size changes; compressed MediaRecorder capture is offered only when lossy exports are allowed. Screen capture is absent on mobile browsers; camera is offered. Existing application shell includes projects/media/sequences, panels, menus, command palette, keyboard shortcuts, desktop/compact layouts, viewer and playback controls, AI panel and MCP dialog. Network boundary is user/provider direct for AI, and browser-to-configured-server/bridge for MCP. Secrets default to session storage; remembering them opts into local storage (not a platform secure vault).

## Native current status

- `android-native/app/(tabs)/index.tsx` is the sole product screen. It selects **one PNG**, retains the selected file bytes, presents the evidence image or generated negative preview in a React Native `Image`, runs a fixed Negative operation, and offers user-selected SAF export as 16-bit RGB PNG. There are no AI, MCP, video-input/camera/screen-capture, project navigation, filter, playback, configuration, or application menu screens. Tabs contain only `index` and the tab bar is hidden. Root is an Expo Router stack with this one tab group and an OAuth callback route; this route handles app/account OAuth and is not MCP authorization.
- `lib/engine/imagePipeline.ts` hashes exact original file bytes, decodes PNG samples via the project exact PNG decoder, applies `255 - RGB` while passing alpha through, quantizes/clamps to RGB16 using `Math.round(v * 257)`, encodes PNG and verifies its in-memory samples. `savePngWithReadBack` writes through Android Storage Access Framework, reads the chosen file back, then `verifyPngExport` compares every 16-bit RGB sample and MD5. This is a narrowly scoped, code-level export-verification claim. The on-screen `<Image>` is only a local display preview; it does not validate pixels, decoded evidence authenticity, or broad forensic processing. The “PIXELS VERIFIED” label follows presence of the pipeline result (including the in-memory case); a separate status says whether the saved file was read back and verified. README explicitly says PNG stills/Negative only and that no native-device run has yet been done.
- `app.config.ts` declares Android `blockedPermissions` for `android.permission.INTERNET` and `ACCESS_NETWORK_STATE`, and `permissions: []`; README describes the workflow as offline with no evidence upload/account/AI. This is an intentional product boundary, not an implemented offline AI mode. The managed starter still has server/database/API scaffolding and network-related dependencies in `package.json`; README says this scaffold is unused. `_core/api.ts`, `_core/auth.ts` and the OAuth route are template account/server mechanisms, not wired into the evidence screen; do not mistake them for AI/MCP or forensic evidence-network functionality.
- Native tests currently cover six source-level cases in `tests/forensics/imagePipeline.test.ts` (hash vectors, exact tiny PNG decoding, end-to-end Negative/in-memory export sample check, float-to-RGB16 quantization, PNG 16-bit encode/decode, SAF base64 byte round trip). They are not runtime/device tests and do not establish parity with the browser's video/filter/AI/MCP stack.

## Specific gaps

1. No native AI-provider settings, streaming conversation, model/tool loop, frame-sharing control, approval UI, checkpoint/rollback or AI audit log. No native equivalent of the web's AI tools or filter-schema validation.
2. No MCP client, server, bridge, WebMCP/page API, server catalog, resource/prompt support, per-client policy/grants, credentials management or MCP OAuth/elicitation UI. The existing native OAuth callback is unrelated app login.
3. No capture. Web camera/screen input, recording controls, lossless AVI writing and compressed recorder path are absent; Android's existing PNG processing cannot substitute for them.
4. No product-level native configuration/navigation corresponding to web menus, command palette, panels, projects/chains, media/image-sequence loading, player, or AI/MCP settings. A hidden one-item tab navigator is routing scaffolding, not parity navigation.
5. No web-equivalent source formats or evidence/project concepts in the native workflow: the picker is constrained to `image/png`, and README states video, projects, reports and remaining filters are unimplemented. Therefore no native AI can inspect web-style source metadata, chain output statistics or reports today.
6. Native preview and verified export are different: React Native `Image` only displays the selected/generated PNG. Saved-output equality check is performed after export; the current tests additionally verify in-memory encode/decode. Neither is evidence that the Android display pixels, color management, capture path or every source format match the web engine.

## Dependencies and risks

- **Forensic exactness:** preserve original bytes and hashes separately from decoded/processed pixels; retain the native “source unchanged” invariant and exact saved-file readback. The web AI may inspect rendered, color-converted/filtered snapshots and its model-facing JPEG attachment is a lossy preview. Never equate model visual inspection, playback, screenshots or `<Image>` rendering with exact frame statistics/hash or verified export. A video port needs specified decode, timestamps/frame indexing, color matrix/range/chroma siting, transfer/HDR, alpha, crop/scale and pixel rounding; use vectors and browser-reference fixtures for parity rather than visual-only matching. Lossless capture means no compression after the browser-delivered frame, not sensor-native/raw capture; skipped frames and display-size changes are explicitly possible and must be recorded.
- **Offline/security boundary:** native currently blocks Android Internet permission. Cloud AI, remote MCP and bridge networking conflict with the stated offline workflow and require an explicit product/security decision, consent and a changed permission boundary—not a silent implementation. Network enablement must identify exactly which user message, case/project metadata, tool results or images leave device, constrain endpoints/redirects, protect API keys/tokens using Android secure storage, support key deletion, TLS and clear failure behavior. MCP tool outputs are untrusted; connected tools may read/write data or have external side effects. Enforce connection grants, read-only/approval policy, frame consent, cancellation and audit events on-device, not just UI labels.
- **Local AI feasibility:** a local network endpoint such as the web Ollama setting is not automatically available on Android, and a local server on `localhost` would refer to the handset. On-device model execution needs an explicitly selected runtime/model, memory/thermal/battery sizing and tool-call capability; that would be new native behavior, not parity achieved by copying provider settings. Any cloud option makes offline badge/README and permission declarations inaccurate.
- **Android capture feasibility:** CameraX/Camera2 can provide camera frames but not the browser's camera+screen symmetry. Screen capture uses Android `MediaProjection` with a system prompt, consent and foreground-service/lifecycle constraints; frame delivery/encoding, rotation, display resize and dropped-frame reporting require device-level characterization. Lossless RGB AVI can consume substantial storage/bandwidth and needs streaming file output, limits, cleanup after cancellation and storage-access handling. Audio parity is not implied (web lossless AVI does not record audio; compressed path may).
- **OAuth/MCP:** browser OAuth depends on popup, redirect page and localStorage handoff; native MCP OAuth would need a separately specified native OAuth flow (system browser/deep link, PKCE, issuer/resource validation, secure token storage/refresh) and server CORS/network permissions. Existing `/api/oauth/mobile` account sign-in must not be reused as if it were MCP OAuth.
- **Product scope / test status:** implementing AI/MCP before the chain/filter/source model, exports, reports and native audit log would expose empty or semantically different tools. Build and UI success do not prove native pixels or API security; this audit ran no app/runtime tests and no tests were run by this task.

## Recommended port sequence (small, testable)

1. **Define native capability boundary and navigation contracts:** write capability flags/screens and a native project/evidence/session model for PNG-first workflow. Keep offline/no-network as the default and expose explicit unavailable status for web-only AI/MCP/capture; add navigation tests before adding new services.
2. **Establish forensic parity substrate:** port/reference source metadata, exact frame/pixel representation, operation schema and per-operation deterministic fixtures. First compare existing Negative path to browser output at boundary values and varied PNG depths/color types; keep preview labeling separate from processing and saved-file verification.
3. **Port navigation and safe project tools:** add project/chain/history, viewer frame navigation, playback only after media/timebase support, then read-only AI-like inspection APIs. Test each tool against the app state and prohibit mutation in read-only mode. Avoid exposing nonexistent formats/capabilities.
4. **Add native audit/undo/approval foundations:** record request/tool/action/result, source/frame scope, provider/endpoint, image sharing and verification evidence; implement undo/checkpoint and permission prompts. Test rejection, cancellation, app backgrounding and rollback before model integration.
5. **Capture as a separate Android feature:** implement user-consented CameraX capture first, characterize timestamps/rotation/resolution and frame drops, stream lossless output to SAF, verify the saved file and audit capture metadata. Treat MediaProjection screen capture as a later independently consented step. No compressed path unless lossy operation is explicitly permitted and reported.
6. **AI behind an explicit capability/network choice:** prototype on-device inference only if a supported local model/runtime with tool use fits target devices; start with read-only tools, no frame images, then add per-call opt-in frame sharing. Cloud provider connections should be a separately approved online mode with Android Internet permission, exact outbound-data disclosure, secure key storage and transport/security review. Port ask/agent distinction, streaming cancellation, schema validation, approvals and audit before write tools.
7. **MCP last and isolated:** port outbound MCP client basics for user-configured remote servers only after network approval and policy/audit protections; add auth/OAuth, elicitation and transport compatibility in increments. External MCP server/bridge operation and browser-only WebMCP should be separately scoped; do not claim them as automatic Android equivalents.
