# Parity audit: Cases, projects, history, provenance, reports and export

**Area ID:** `cases-projects-reports`
**Comparison rule:** The existing browser implementation is the intended product behavior. This is a source inspection only: no source was changed, dependencies were not installed, and no runtime tests were run.

## Scope

**Web:** `src/app/session.ts`, `store.ts`, `report.ts`, `actions.ts`, `src/engine/writers/writers.ts`, `src/shared/project.ts`, `src/panels/HistoryPanel.ts`; directly relevant data contracts and wiring in `src/shared/types.ts`, `src/app/App.ts`, `context.ts`, engine hashing/snapshot/write paths, and existing project/writer/hash test references.

**Native:** `android-native/lib/project/evidenceIO.ts`, `android-native/lib/engine/imagePipeline.ts`, PNG codec and hash modules, `android-native/app/(tabs)/index.tsx`, app routing, and `android-native/tests/forensics/imagePipeline.test.ts`. `android-native/lib/reports/` does not exist. Native routing exposes one Evidence screen; there are no project/report modules or history UI in the inspected scope.

## Intended browser behavior

- **Case/project metadata:** Project Information edits project name, case number, exhibit/item, examiner, agency/lab and notes. Project documents carry app/schema, created/modified timestamps, chains/filter parameters, source references, bookmarks and an optional AI audit log.
- **Project portability:** Open Project sniffs the file, parses JSON, validates chain/filter/source structure and rejects future schemas or unknown filters; it applies version migration while pinning legacy parameters to preserve old results, normalizes filters, and prompts before discarding dirty work. Save Project writes the project document (`.lfp`/JSON) to a selected file where supported or downloads it. It does **not** embed source media: it records names, sizes, timestamps/types, options and available hashes. Reopen may prompt to relink media by filename; differing file sizes are warned about, but the relinker does not establish byte identity by hash.
- **Crash/session recovery:** `Session` autosaves project JSON plus some source `File` objects in IndexedDB. Files are included only while under the 768 MiB accumulated media cap, and session recovery requires a nonempty chain. This is browser-profile storage, distinct from the portable project file.
- **Undoable edit history and filter tree:** Store snapshots chains, bookmarks, source references, case info and name; supports undo/redo, coalesces rapid edits, caps undo at 300 entries, and keeps AI audit entries outside undo. HistoryPanel displays chains and ordered filters, lets users select/configure, collapse chains, enable/disable and move/duplicate/copy/paste/remove filters, create a chain from a step, and rename/duplicate/open/delete chains. This is processing-history UI, not a chronological activity log.
- **Evidence provenance:** Source info exposes file/format/codec/streams, dimensions, frame rate, duration, decoding/conversion metadata and hashes. Hash File computes MD5, SHA-1 and SHA-256 on the complete original file; hash output frames generates a text listing of MD5s over each displayed 8-bit RGB output frame. The report can compute a missing hash for a single loaded file; multi-file sources are explicitly marked not computed. Metadata hashes are provenance aids, not a signed chain-of-custody record.
- **Reports:** Generate Report builds a self-contained printable HTML report containing case metadata, evidence name/type/file metadata/hashes and decoder details, ordered filters with parameters/descriptions/categories/references, active/disabled status, rendered step snapshots and final outputs, bookmarks, optional AI request/model/action/frame-sharing history, and methodology/integrity caveats. “Open / Print” supports browser print-to-PDF; Save Report downloads HTML. Report imagery is not uniformly forensic output: when lossless-only is enabled it embeds full-resolution uncompressed PNG snapshots from engine pixels; otherwise intermediate images are scaled JPEG previews, while chain-final images remain full-resolution PNG. Snapshots show selected/current or bookmarked frames, not a full video record.
- **Export:** Write Video/Images supports multiple image, sequence/ZIP and video formats, frame ranges/FPS/quality, browser file-picker or staged/download paths, cancellation and size/storage handling. Lossless formats include PNG/TIFF/BMP and uncompressed AVI; lossy formats are gated by preference. Verification is available for lossless output: writers read the written file back (or parse AVI / ZIP entries) and compare every frame/sample against expected MD5 values. `WriteResult.verified` reports success/failure; a failed/cancelled post-write verification does not silently certify an export. This exact read-back verification is distinct from a viewer preview or a hash alone.

## Native implementation now

- The Android screen accepts one PNG through Expo DocumentPicker, copies it to cache, reads its bytes, and checks picker-reported size if provided. It retains the bytes in screen state for processing and source hashing; it does not overwrite the source.
- `decodePngExact` parses PNG chunks, checks critical chunk CRCs, inflates image data, supports PNG color types/depths and Adam7, and preserves 16-bit fractions in a float RGBA frame; it flags APNG as animated, and the current export pipeline rejects animated PNG. It does not constitute broad image/video decoder support.
- The sole processing action is the reference Negative (`255 - RGB`, alpha passed through). `runNegativeExport` computes source file MD5/SHA-1/SHA-256, encodes 16-bit RGB PNG, verifies the in-memory PNG and returns an MD5 over samples. The app then saves through Android SAF and reads that exact destination back, checking every decoded sample and hash. If the user cancels destination selection, it retains an in-session verified export and labels it “not saved.”
- The displayed React Native `Image` is a viewer preview of the selected file or generated PNG. It is not itself pixel-exact processing, a decoder validation, or saved-file verification. Exactness claims belong only to `decodePngExact` and the explicit in-memory/SAF read-back checks.
- No portable project schema/open/save/relink, autosession or case metadata, undo/redo, multi-step chain/filter HistoryPanel, bookmarks, source-info report, AI provenance, HTML/PDF report, per-frame video hashes, video/media export catalogue, or general export verifier is present in the inspected Android feature paths. `writePreviewPng` writes a temporary cache image; it is not project persistence or a user-selected output.
- Existing native tests cover hash vectors, one small generated RGB PNG fixture, a Negative conversion, RGB16 clamping/rounding, PNG sample round-trip, and Base64 round-trip. They do not test an Android SAF round trip, state restoration, projects, reports, output against a browser golden, or full media workflows.

## Specific gaps

1. No case/project data model or migration/validation, save/open/share/import, recovery, dirty-state protection, or source relinking exists natively.
2. No undo/redo or chain/filter history exists; Android has one fixed action, not the browser's editable processing graph.
3. The only input/output workflow is single still PNG → Negative → 16-bit RGB PNG. Browser parity requires the much broader image/sequence/video/DVR source model and configurable processing graph before project/report parity is meaningful.
4. Native provenance currently reports source byte hashes and output sample hash for one transient run; it does not persist metadata, decoder details, processing parameters as a case record, frame hashes, bookmarks, or operator actions.
5. No report artifact exists. The native preview and success labels cannot substitute for a report with clearly identified preview images, processing parameters, and verification scope.
6. Native PNG output verification covers pixel samples/dimensions by decode and sample comparison, but not a manifest/report, file-hash provenance for output, multiple formats, video frame-by-frame read-back, ZIP integrity, cancellation/error recovery, or a reusable verification result record.
7. Project-relink parity must improve on browser behavior if forensic byte identity is a requirement: browser relinking currently matches case-insensitive filenames and warns only on size mismatch; it does not recompute/require stored hash equality before binding the project to a selected file.

## Dependencies and risks

- **Forensic exactness:** A React Native `Image` rendering path is only preview. Never present its display pixels as processed or verified evidence. Preserve original bytes, distinguish source-file hashes from decoded-pixel hashes and output-file hashes, record exact algorithms and byte/sample domains, and only claim saved-output verification after reopening and comparing the destination bytes/samples. For relinking, filename/size are insufficient; require a hash match or explicit examiner-confirmed mismatch workflow, with multi-file sequence members individually identified and hashed.
- **Decoder/processing parity:** Android’s exact PNG decoder deliberately works “as stored” (ignoring gamma/ICC per module comments) and its RGBA/float conversion and 16-bit rounding must be compared with the web loader/writer on fixtures. A mathematically similar operation is not proof of identical browser/native output. PNG/APNG, palette/transparency, 16-bit, malformed chunks, interlacing, color metadata and alpha semantics need explicit expected behavior.
- **Offline and sensitive data:** The native image path itself reads/hashes/processes locally and the UI says no upload; preserve this property for project/report features. Case identifiers, examiner notes, source paths/URIs, hashes and embedded snapshots are sensitive. Keep media out of logs/analytics/network requests, make any sharing/export user initiated, consider Android backup/cache cleanup and encryption at rest, and communicate that the current cache/session model is not a durable case archive. Browser IndexedDB autosession can retain original files in the profile; native should make retention and clear/delete behavior explicit.
- **Android storage feasibility:** Expo DocumentPicker/SAF is suitable for user-granted local files, but projects with many/large videos cannot be loaded wholesale as Base64/JS `Uint8Array` without memory pressure. Use content URIs and streaming/native file IO where possible; SAF permission lifetime, URI relinking, directory/provider quirks, duplicate names, Android scoped-storage restrictions and partial writes require device-level tests. The present helper reads a complete file through Base64 and also keeps byte arrays in JS memory, so scale is currently constrained.
- **Report portability and security:** A self-contained HTML report must escape all user/evidence strings and decide whether image data is embedded; large lossless snapshots can make huge reports. Reports should be reproducible from saved state and identify snapshots as selected-frame previews versus verified export data. Native print/PDF or share-sheet export should not silently upload sensitive content.
- **Schema parity and cross-platform behavior:** Reuse/port the web schema and migration rules deliberately, rather than creating a superficially similar Android-only document. Pin historical defaults so reopening does not change output. Keep browser-vs-Android decoder/conversion differences visible in the report.
- **No runtime assurance from this audit:** Findings are based on checked source paths and test definitions; no build, device run, or runtime suite was executed.

## Recommended port sequence (small, testable increments)

1. Define a platform-neutral project/case DTO matching `ProjectDoc` and a native validator/migrator aligned with `PROJECT_SCHEMA`; add golden JSON fixtures for current, legacy, malformed, unknown-filter and future-schema documents. Do not claim parity until web/native round-trip the same fixture without changing filters or parameters.
2. Implement local project create/edit/dirty state and atomic save/open through SAF. Start with project JSON only (references, not copied evidence); add cancellation, malformed-file and write/read failure handling plus explicit distinction between portable project and autosession.
3. Add a local autosession repository and clear/recovery policy. Persist only media references or explicitly bounded cache copies; test process restart and storage failure. Make private evidence retention user-visible.
4. Implement source records and robust relinking: stable per-file identity, streaming MD5/SHA-1/SHA-256, required hash comparison when available, explicit changed/missing/ambiguous states, sequence ordering, and no silent wrong-file binding.
5. Add a minimal editable chain/filter document and one undo/redo-tested action (Negative), then incremental filter/history UI. Keep rendering and preview labeled separately from validated processing.
6. Add evidence info and provenance records (original file hashes; format/dimensions/decoder/color handling; filter params; output hash domains; operation timestamps). Add deterministic native golden comparisons with browser fixtures before expanding codecs.
7. Generalize verified export: write a 16-bit PNG to SAF, reopen the actual output, compare dimensions and all samples, hash the complete saved file, and persist a verification record. Test failed/short/modified read-back and cancellation. Extend formats/videos only after a native decoder/writer and frame-level verification path exists.
8. Port bookmarks/frame indexing as a separate step when video chains exist; test chain deletion, undo/redo, frame bounds and project round-trip.
9. Add an HTML report from the serialized project/provenance record, then Android print/PDF/share. Include all caveats and distinguish full-resolution verified output from scaled viewer/report previews. Validate escaping, missing sources, large reports, offline behavior and no implicit upload.

## Tests needed

- **Existing web reference coverage to preserve:** `tests/sniff.test.ts` (`validateProject`, `migrateProject` current/invalid/legacy/idempotence checks); `tests/writers.test.ts` (lossless encode/decode and sample hashes); `tests/hash.test.ts`; `tests/e2e/lossless.py` (read-back verification and external frame/sample checks); `tests/e2e/fidelity.py` (float precision/export fidelity). These are source references, not tests run for this audit.
- **Existing native baseline:** `android-native/tests/forensics/imagePipeline.test.ts`, especially “runs Negative on-device, hashes original bytes, and verifies the written 16-bit PNG samples,” plus the generated `compressedRgbPng` fixture, hash-vector checks, sample round-trip and Base64 binary round-trip.
- **Add native project tests:** `validateProject`/migration parity fixtures for all schemas; serialized round-trip preserving exact params, case fields, hashes, bookmarks and AI log; future/unknown schema rejection; dirty/open cancellation; atomic save/recovery/clear; legacy defaults remain output-identical.
- **Add native evidence-IO tests/device tests:** source selection byte-for-byte/hash vectors; SAF create-write-reopen compares full file bytes and decoded samples; permission denial/cancel, duplicate-name/provider URI, truncated/short writes, storage-full and process-death/relink cases. Mocked unit tests alone are insufficient for SAF provider behavior.
- **Add provenance/relink tests:** same name + changed bytes, same size + changed bytes, renamed identical bytes, multi-file sequence ordering/missing item, hash recomputation and mismatch confirmation; assert no silent substitution.
- **Add preview-vs-processing tests:** `decodePngExact` and Negative pixel/sample goldens for 8/16-bit RGB, grayscale, palette/transparency, alpha, interlaced, APNG rejection, corrupt CRC/truncated chunks, ICC/gAMA metadata policy and boundary values; explicitly assert RN `Image` preview is not used to generate or verify output.
- **Add export/report tests:** verify saved bytes and all output samples plus output-file hash; deliberate mutation/corruption must fail; report HTML escaping, required case/evidence/chain/hash/parameter/bookmark sections, unavailable sources, AI history, generation timestamps, disclosure of lossy/scaled preview snapshots, offline generation and no network calls. Add browser/native fixture comparison for exact output where the same decoded samples and operation are intended to match.
