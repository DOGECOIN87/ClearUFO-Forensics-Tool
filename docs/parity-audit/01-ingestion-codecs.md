# Parity audit 01 — Evidence ingestion, containers, still-image/video codecs

**ID:** `ingestion-codecs`
**Repository:** `/home/ubuntu/projects/clearufo-forensics`
**Audit basis:** source inspection only. No source edits, dependency installation, or runtime tests were performed. The browser implementation is treated as the intended behavior.

## Scope

**Web:** `src/app/capture.ts`, `src/app/staging.ts`, `src/engine/sources/`, `src/engine/worker.ts`, `src/shared/sniff.ts`, `src/shared/formats.ts`, `src/shared/codecs/`. Directly relevant dependencies read include app `actions.ts`/`engineClient.ts`, engine staging, source dispatcher and frame/source helpers, image/AVI/DVR/Mediabunny decoders, `src/engine/writers/writers.ts` references from tests/catalog, and shared staging.
**Android:** `android-native/lib/project/evidenceIO.ts`, `android-native/lib/codecs/`, `android-native/lib/engine/imagePipeline.ts`; implementation call sites inspected in `android-native/app/(tabs)/index.tsx`, with `android-native/lib/engine/hash.ts` and native tests.

## Original browser behavior (reference)

- **Content-based routing:** `sniffFile`/`sniffBytes` examines up to 4,096 leading bytes rather than trusting extensions/MIME. It distinguishes projects, common still images, many video/container and audio signatures, archives/documents, and unknown binary. `actions.ts` routes images and videos, explains definite refusals, and lets the user try unknown binary as media—important for proprietary DVR files. Identification is not a guarantee of decode support.
- **Still images and sequences:** `openImage` accepts PNG, JPEG, GIF, BMP, TIFF, WebP, AVIF, HEIF, ICO and image MIME fallback. PNG is decoded in-app from stored samples (all standard color types/depths 1–16, `tRNS`, Adam7); TIFF uses `utif2`, retaining 16-bit integer/32-bit float samples for supported chunky gray/RGB(A) layouts and otherwise using its 8-bit conversion. Other formats use browser decoding; a verified WebCodecs `VideoFrame` path may expose exact pixels, otherwise canvas readback is used. Multi-page TIFF and animated GIF/WebP/APNG are handled where implemented/browser-supported (up to 5,000 animation frames); sequences are natural-sorted, normalized to first-frame dimensions by top-left placement on black, and exposed as frame sequences. EXIF/JPEG structure metadata is surfaced. Orientation and color profiles are not applied: the stated intent is pixels “as stored.”
- **Video/container ingestion:** `openSource` handles indexed/scanned AVI (OpenDML/AVI 1.0), MJPEG, uncompressed RGB/gray and multiple raw YUV layouts; H.264/H.265 AVI elementary data is converted/remuxed. `MediabunnySource` demuxes its `ALL_FORMATS` supported inputs (for example MP4/MOV, WebM/MKV, MPEG-TS) and uses WebCodecs to index frames by packet presentation timestamps, inspect streams/metadata, and decode. `Convert DVR` recovers Hikvision/MPEG-PS, Dahua DHAV, raw H.264/H.265 Annex B and concatenated MJPEG; H.264/H.265 conversion is a stream-copy remux to MP4, not re-encoding. MPEG-4 Part 2 AVI is explicitly unsupported. If WebCodecs cannot decode, the HTML media-element fallback is explicitly time-based/approximate and canvas conversion bypasses the loader’s controlled YUV options. This preview/playback fallback is **not** equivalent to frame-accurate verified processing. Software WebCodecs can expose full decoded YUV planes for ClearUFO’s own matrix/range/chroma/HDR conversion; browser/hardware RGB and canvas paths may be browser-converted and lower precision.
- **Capture and output:** `captureLossless` captures camera/screen frames via `MediaStreamTrackProcessor`, `requestVideoFrameCallback`, or animation-frame fallback, stores browser-delivered frames as uncompressed RGB24 AVI at 1:1, and writes to a user-picked file or browser OPFS staging, falling back to bounded memory. It records no audio; slow writes may skip frames; changing dimensions are cropped/padded, never scaled. “Lossless” therefore describes stored captured frame samples, not a source-bitstream/audio/timestamp-preserving recording. `FORMATS` offers raw AVI, uncompressed TIFF 8/16/float, PNG 8/16, BMP, and lossy MJPEG AVI, MP4, WebM, JPEG and WebP. Image sequences are stored ZIP/ZIP64. Sinks stream/patch disk or OPFS files where available; staging probes read-back, tracks quota, locks entries across tabs and supports cleanup. This is a storage/export feature, not source-media authenticity verification.

## Current native implementation

`index.tsx` exposes one explicit flow: choose a single PNG (`DocumentPicker` MIME filter), retain its read bytes, show a React Native `Image` preview, run the on-device Negative formula, write a 16-bit RGB PNG, choose an Android SAF directory, reread the saved output, then compare every decoded RGB sample against expected samples. Original-file MD5/SHA-1/SHA-256 are calculated from imported bytes. The **preview is only a platform-rendered image preview**; sample verification is provided by `runNegativeExport`/`verifyPngExport`, not by the preview.

`runNegativeExport` rejects non-PNG and APNG, hashes source bytes, uses `decodePngExact`, applies `255 - channel` to RGB, converts to 16-bit with `Math.round(v * 257)`/clamping, writes with `encodePNG`, and checks its in-memory samples. `verifyPngExport` uses the restricted local RGB stored-deflate `decodePNG` reader and checks dimensions, sample bytes, and sample MD5. Native exact PNG input decoder supports the same color types/depths/interlace/transparency intent as the web PNG decoder and uses bundled `fflate` rather than browser `DecompressionStream`. The native writer/verification reader are deliberately narrower than the input decoder: RGB 8/16-bit, stored-deflate/filter-0 output only.

File I/O is whole-file: `readUriAsBytes` obtains a Base64 string then decodes another byte buffer; PNG output is Base64-written, read back, and retained. Save checks byte length before pixel verification; it does **not** establish byte-for-byte equality of the saved PNG or save its output-file hash. The screen says “PNG still images only.” No source ingestion sniffing, TIFF/JPEG/other still decode, sequence, video/container/DVR import, camera/screen recording, video/image-sequence export catalog, or OPFS-like staging implementation is present in the inspected native feature path. `expo-video` in dependencies alone would provide playback capability, not forensic frame indexing/processing parity.

## Specific gaps

1. **Ingestion contract:** no native magic-byte `Sniffed` model, multi-file/sequence routing, project-vs-media/wrong-picker recovery, or unknown-binary DVR recovery; MIME-filtered selection is narrower than content-led browser routing.
2. **Still media:** only PNG is processed; no JPEG metadata/EXIF, TIFF pages/full-precision paths, BMP, GIF/WebP/AVIF/HEIF/ICO, animated-image handling, or natural-sorted image sequences. Native PNG preserves/uses RGB values for this one transform but drops source alpha in output; its rendered preview is not sample evidence.
3. **Video and containers:** no native source provider, demuxer, frame/PTS table, codec metadata, YUV conversion controls, AVI parser, DVR scanner/remuxer, or source-fidelity warnings. A player preview, if added, must not be labelled frame-accurate forensic processing.
4. **Recording/exports/storage:** no live capture or uncompressed AVI/OpenDML writer; no TIFF/BMP/ZIP, MP4/WebM/MJPEG/JPEG/WebP export paths, export estimates, or scalable staging. Current SAF export is PNG-only.
5. **Verification semantics:** native pixel read-back is a meaningful check of processed sample equality, but it is not original-file identity, output byte identity, decoder correctness across formats, or proof of a recorded video’s complete frame/audio provenance. The native source hash only identifies bytes returned by picker/cache I/O.

## Dependencies and risks

- Forensic determinism must be specified per format. Web’s custom PNG sample decode is stronger than platform preview; TIFF’s “full precision” is conditional; browser image/canvas and hardware video decode may color-manage, orient, down-convert, or conceal errors. Match the original’s declared behavior, expose decode path/warnings, and never promote playback pixels to verified samples without parity fixtures.
- Android SAF URIs can be provider-backed rather than ordinary files. Current `copyToCacheDirectory: true` improves readability but can consume substantial temporary storage; Base64 strings, decoded source arrays, decompressed PNG, RGBA float arrays, expected 16-bit samples and output coexist. Large inputs and decompression bombs can exhaust memory. Add byte/pixel/dimension/decompression limits, cancellation and streaming before broadening formats; consider native streaming file/hash/decode APIs instead of a large JS `File` copy.
- Offline posture is favorable: app config blocks Android INTERNET and the current evidence path is local; `fflate` is bundled. Keep parsers/codecs bundled and validate dependency/license/security and malformed-file behavior. Do not infer that every project subsystem is offline solely from this area.
- Porting browser APIs is not mechanical: Android lacks WebCodecs, OPFS, File System Access API, Web Locks, `VideoFrame`, and MediaStreamTrackProcessor equivalents. Android MediaCodec/MediaExtractor or a vetted bundled demux/decode library can cover common video but codec/container coverage varies by OS/device; hardware color conversion and error concealment threaten repeatability. MediaProjection requires permission/foreground-service UX, camera capture requires permission/device handling, and encoding uncompressed AVI can produce very large files. Probe device codec support and record provenance/limitations.
- `fflate` enables PNG inflation in the JS runtime but the current full-buffer pipeline is not a scalable large-file architecture. Pure-TS hashing is tested against standard vectors, but performance on large mobile files needs profiling.

## Recommended port sequence

1. **Define the parity and verification contract** (source bytes vs decoded samples vs preview vs output bytes); add shared golden fixtures and limits. Preserve original-byte hashing before any transform; show when a source is unsupported rather than silently converting it.
2. **Complete PNG ingestion hardening/parity:** content sniff and reasoned errors; verify all PNG color/depth/filter/Adam7/`tRNS` cases, 16-bit edge values, corrupt/truncated data, APNG refusal, alpha behavior, and large-file limits. Separate preview from the exact decode result in UI labels.
3. **Port deterministic still formats one at a time:** BMP then TIFF with explicitly enumerated supported variants/pages/precision and metadata; add JPEG decode/EXIF with the original orientation/profile policy; add animated formats/sequences only with frame-order/delay fixtures and explicit decode-path warnings.
4. **Add file/source abstraction and metadata before video UI:** URI-backed read/seek, sniff routing, sizes/hashes, stable frame table and failure reporting; parity fixtures for AVI indexes/raw layouts/MJPEG and PTS/color metadata.
5. **Choose native video stack via a capability spike:** prove exact repeatable frame extraction and timestamp order on representative H.264/HEVC codecs/containers across minimum and current Android versions. Then port raw AVI/MJPEG, common demuxing, and DVR stream-copy/remux separately; retain warning distinctions for platform/hardware RGB fallback. Do not promise all `ALL_FORMATS` without a measured matrix.
6. **Port outputs and capture last:** deterministic still writers/read-back verification first, then AVI/OpenDML streaming and storage-limit policy. Add Android SAF streaming and cleanup. Treat camera and MediaProjection capture as a separate permission/provenance feature; explicitly document skipped frames, audio absence, clocks, resolution changes and encoding.
